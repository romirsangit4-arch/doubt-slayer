# JEE Diagnostic Tutor — Full Project Blueprint

---

## 1. Product Thesis

We are not building an ed-tech app. We are building an **AI-native tutoring service** where the AI is the tutor, the diagnostician, and the bookkeeper. The business is a conversation. A student pays for a session where an AI finds their exact fault line in a JEE problem, repairs it with micro-examples, and co-constructs the solution with them. The AI makes all pedagogical decisions in real time. Human involvement is limited to billing and quality oversight.

---

## 2. The Pedagogical Engine (Core IP)

This is the product. The code is just the container.

### 2.1 The Three-Act Session State Machine

Every session moves through three acts. The backend maintains the act in a `session_state` field.

| Act | Name | AI Behavior | Student Experience |
|-----|------|-------------|-------------------|
| **Act 1** | **Diagnosis** | Asks 2–4 sharp, multiple-choice or one-word questions targeting the exact step where the solution breaks. | "Why did you take the moment about point A and not B?" |
| **Act 2** | **Fragment Repair** | Generates a 2-minute micro-example targeting the exact gap. Waits for student to solve it. | Solves a tiny, isolated problem in chat. |
| **Act 3** | **Reconstruction** | Returns to the original problem. Co-builds solution via Socratic questioning. Step size adapts to student confidence. | Rebuilds the original problem step-by-step with AI only asking, never telling. |

### 2.2 Conversation Discipline

- **No paragraphs.** AI responses are capped at 2–3 lines (max 60 words).
- **No direct answers.** The AI must never say "The answer is 5 m/s²." It asks: "What is the net force? Divide by mass."
- **Variable Granularity.** The AI internally scores student confidence (0–1) per step. High confidence → next prompt asks for 2–3 steps at once. Low confidence → next prompt isolates a single variable substitution.
- **The 3-Strike Rule.** If a student fails a gate in Act 3 three times, the AI does not reveal the answer. It retreats to a new micro-example (Act 2 loop), repairs the deeper sub-gap, and returns.

### 2.3 JEE-Specific Adaptations

- **Image-first input.** JEE problems are diagram-heavy. The student must be able to snap a photo of HC Verma, Irodov, or coaching sheets.
- **Syllabus-aware taxonomy.** The AI does not guess topics. It maps every problem to a node in the JEE (Main + Advanced) syllabus tree. This enables the Student Knowledge Map.
- **Hinglish tolerance.** Students often type in Romanized Hindi-English mix. The AI responds in crisp English but understands hybrid input.

### 4.2 Component Breakdown

**Frontend (Next.js)**
- `ChatInterface`: Core component. Handles SSE stream rendering, typing indicators, and message bubbles.
- `ImageUploader`: Compresses images client-side (max 2MB), requests signed URL from backend, uploads directly to GCS.
- `TopicSelector`: Searchable JEE syllabus tree. Used when student skips image upload.
- `SessionReview`: Post-session "Mastery Card" with exportable summary.
- `PaywallModal`: Triggered after Act 1 completion of free session.

**Backend (FastAPI)**
- `orchestrator.py`: Session state machine. Decides which act to invoke based on conversation history.
- `diagnostic_engine.py`: Act 1. Parses problem + student responses to output `ConceptualGap` objects.
- `fragment_builder.py`: Act 2. Generates micro-examples given a gap.
- `reconstruction_guide.py`: Act 3. Socratic scaffolding with variable step size.
- `image_parser.py`: Pre-processes image for Gemini vision. Adds OCR confidence metadata.
- `payment_service.py`: Razorpay order creation, webhook verification, entitlement checks.
- `knowledge_map.py`: Updates `StudentKnowledgeMap` after every session.

## 5. Data Architecture (Firestore)

### 5.1 Collections

```
students/{student_id}
  - phone_number: string
  - target_exam: "JEE_MAIN" | "JEE_ADVANCED" | "CLASS_11" | "CLASS_12"
  - created_at: timestamp
  - knowledge_map: map<<topic_id, {mastery_score: float, last_assessed: timestamp}>

sessions/{session_id}
  - student_id: ref
  - status: "DIAGNOSING" | "REPAIRING" | "RECONSTRUCTING" | "COMPLETED" | "ABANDONED"
  - input_type: "IMAGE" | "TEXT" | "TOPIC"
  - problem_image_url: string (GCS)
  - problem_text: string (OCR + human fallback)
  - detected_topic: ref(syllabus)
  - detected_subtopic: ref(syllabus)
  - gaps_found: array<<map>
  - current_act: int (1-3)
  - step_confidence: float (0-1, rolling)
  - created_at: timestamp
  - ended_at: timestamp
  - paid: boolean

messages/{message_id} (subcollection under sessions)
  - role: "system" | "ai" | "student"
  - content: string
  - message_type: "diagnostic_question" | "micro_example" | "scaffold_prompt" | "hint" | "student_answer"
  - timestamp: timestamp
  - act: int

micro_examples/{example_id} (subcollection under sessions)
  - gap_id: string
  - problem_statement: string
  - solution_steps: array<string>
  - student_solved_correctly: boolean

payments/{payment_id}
  - student_id: ref
  - session_id: ref
  - razorpay_order_id: string
  - amount_inr: int
  - status: "created" | "paid" | "failed"
  - verified_at: timestamp
```

### 5.2 Design Reasoning

- **Subcollections for messages:** A JEE session can have 50+ messages. Storing them in a subcollection keeps `sessions` documents small and fast to read.
- **Knowledge map as a map field:** Denormalized for fast reads. Updated incrementally after each session. The AI loads this at session start to personalize diagnostics.
- **No relational joins:** Firestore is document-native. We duplicate minimal data (e.g., `detected_topic` string in `sessions`) to avoid joins.

## 6. AI Service Architecture

### 6.1 Prompt Management Strategy

Prompts are stored as `.txt` files in `/backend/core/prompts/` and versioned by filename.

```
prompts/
├── v1/
│   ├── system_identity.txt      # "You are a stubborn JEE tutor..."
│   ├── act1_diagnostic.txt      # Rules for gap detection
│   ├── act2_fragment.txt        # Rules for micro-example generation
│   ├── act3_reconstruction.txt  # Rules for Socratic scaffolding
│   └── output_schemas/          # JSON schemas for structured output
```

**Reasoning:** Hardcoding prompts in Python strings leads to messy diffs and hotfix hell. Files allow A/B testing and non-engineer tuning.

### 6.2 Structured Output via Gemini

For Act 1 and Act 2, we use Gemini's **JSON mode** (or constrained generation) to guarantee machine-parseable output.

**Act 1 Output Schema:**
```json
{
  "gaps": [
    {
      "concept": "moment of inertia about a moving axis",
      "severity": "blocking",
      "diagnostic_question": "When the axis moves, which theorem must you apply?",
      "expected_answer_type": "one_word"
    }
  ],
  "recommended_act2_topic": "parallel_axis_theorem"
}
```

**Reasoning:** Unstructured text from LLMs is unreliable for state machines. We force JSON so the orchestrator can decide the next act without parsing prose.

### 6.3 Vision Pipeline

1. Student uploads image → Frontend requests signed URL from `/upload-url` → Uploads to GCS.
2. Backend sends image to Gemini with prompt: *"Extract the problem statement, identify the topic using the JEE syllabus, and list the physical quantities and diagrams present."*
3. Output is stored in `sessions.problem_text` and `sessions.detected_topic`.
4. If OCR confidence < 0.8, the AI asks the student: *"I read the problem as [X]. Is this correct?"*

**Reasoning:** JEE problems often have handwritten notes or low-quality scans. A validation step prevents the AI from diagnosing the wrong problem.

### 6.4 Context Window Management

A JEE session can exceed 50 turns. We cannot send the full history every time (cost + latency).

- **Sliding window:** Keep last 10 messages in context.
- **Session summary:** After every act transition, Gemini generates a 100-word summary of the session so far. This summary replaces the dropped history.
- **Knowledge map injection:** The student's mastery scores for the detected topic are injected as a system message at the start of every API call.

## 7. Frontend Architecture

### 7.1 State Management

- **Zustand** for global state: auth, current session, payment status.
- **React Query (TanStack Query)** for server state: message history, session list.
- **Local component state** for input composition.

**Reasoning:** Zustand is lighter than Redux. React Query handles caching, background refetching, and optimistic updates for chat messages.

### 7.2 Real-Time Chat

- **Server-Sent Events (SSE)** for AI response streaming.
- Not WebSockets. SSE is HTTP-based, works through corporate/college firewalls, and is simpler to implement for one-way streaming (AI → student).

### 7.3 Mobile-First Design Choices

- **Input area:** 56dp minimum touch targets. Camera button is primary; keyboard is secondary.
- **Dark mode default:** JEE students study at night. Reduces eye strain and makes the app feel premium.
- **WhatsApp-style bubbles:** Familiar mental model. AI on left, student on right.
- **No infinite scroll in chat:** Sessions are bounded (20–40 min). Paginate history only for "Past Sessions" screen.
- **Image preview:** Thumbnail of uploaded problem stays pinned at top of chat for reference.

### 7.4 PWA Configuration

- `manifest.json` with `display: standalone`.
- Service worker for offline session history viewing.
- Add-to-home-screen prompt after 2nd session.

**Reasoning:** A PWA gives 80% of native app utility with 10% of the effort. For a 2-month hackathon, this is the correct tradeoff.

### 8.2 The Chat Endpoint (`POST /chat/stream`)

This is the heart of the application.

```python
@router.post("/chat/stream")
async def chat_stream(request: ChatRequest):
    # 1. Load session + student knowledge map
    session = await get_session(request.session_id)
    student = await get_student(session.student_id)
    
    # 2. Check payment (if not free session)
    if not await is_entitled(session.student_id):
        raise HTTPException(402, "Payment required")
    
    # 3. Determine act via orchestrator
    act = orchestrator.decide_act(session, request.student_message)
    
    # 4. Build prompt for the act
    prompt = prompt_builder.build(act, session, request.student_message)
    
    # 5. Stream Gemini response
    async def event_generator():
        full_response = ""
        async for chunk in gemini_client.generate_stream(prompt):
            full_response += chunk
            yield f"data: {chunk}\n\n"
        
        # 6. After stream ends, parse structured output, update DB
        parsed = parse_response(full_response, act)
        await save_message(session.id, parsed)
        await update_session_state(session.id, act, parsed)
    
    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

### 8.3 Async Design

- All I/O (DB, Gemini API, Razorpay) is `asyncio`.
- **Reasoning:** A tutoring session is I/O-bound, not CPU-bound. FastAPI's async handling allows a single Cloud Run instance to manage hundreds of concurrent sessions without blocking.

| Concern | Mitigation |

## 13. Anti-Fragility & Fallbacks

| Failure Mode | Fallback |
|--------------|----------|
| **Gemini hallucinates physics** | A `physics_validator` layer checks if Gemini's proposed solution matches the known answer key (if available). If mismatch, prompt is retried with temperature 0.1. |
| **Student uploads unreadable image** | AI asks for clarification. If 2 failures, offer text input fallback. |
| **Student is completely lost** | AI detects 3 consecutive failures and retreats to a simpler prerequisite micro-example. Never gives the answer. |
| **Payment fails** | Retry Razorpay once. If still fails, offer "Pay later" (1 session credit) to reduce drop-off. |
| **High latency (>5s)** | Show typing indicator immediately. Use Gemini 1.5 Flash for Act 1 diagnostics to reduce time-to-first-question. |
| **Gemini API downtime** | Circuit breaker: after 3 failures, show user "Tutor is taking a break. Retry in 2 minutes." |
